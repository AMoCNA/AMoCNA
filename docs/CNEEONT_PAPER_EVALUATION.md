\subsection{Evaluation of real-world applicability}
\label{sec:evaluation-applicability}

The evaluation uses three public microservice suites co-deployed on the Kubernetes testbed: Sock Shop (retail), Online Boutique (e-commerce), and BookInfo (service-mesh sample). Each example is repeated $N \ge 5$ times. We report success rate, wall-clock time-to-remediation, SPARQL query latency (p50/p95), and, for scaling, SLO-violation duration and extra replica-seconds as a cost proxy. Ontology files, the demo catalog, SPARQL queries, and Locust/threshold configs are in the accompanying artifact.

\subsubsection*{Competency questions used in the loops}

\begin{description}
\item[CQ1] Which workloads currently use a catalog-vulnerable image version, and what is the parent \texttt{StatelessWorkloadController}?
\item[CQ2] Which resource has \texttt{ResponseTimeSlaViolatedState}, and what is the highest \texttt{isPartOf} parent Palamedes should scale?
\end{description}

CQ1 is \texttt{cli/resources/sparql/cq-vulnerable-workloads.sparql} (the same join as Palamedes \texttt{find-vulnerable-workloads}). CQ2 is \texttt{cli/resources/sparql/cq-sla-scale-target.sparql}.

\begin{example}\label{example-1}
Image vulnerability patching
\end{example}

This example evaluates the framework's ability to autonomously detect vulnerabilities, map affected containers within the cluster topology, and execute remediation actions. The Log4j CVE motivates the class of threats that never appear as Prometheus gauges; experiments use a deterministic demo catalog so image tags are reproducible.

\subparagraph*{Discussion of Results.}
Metric-only control loops cannot observe image-layer CVEs, because those facts are not time series. Example~1 therefore measures a \emph{capability} the Prometheus/Drools path does not have: SPARQL over \texttt{usesImage}/\texttt{contains} yields the affected workloads (CQ1 topology bindings), and Themis rolls the catalog fix tag. Table~\ref{tab:paper_e1_remediation} reports success rate and time-to-patch for every workload; Table~\ref{tab:paper_e1_sparql} reports CQ1 latency so the RDF hop is quantified rather than assumed negligible. Catalog maintenance is limited to YAML image pairs (\texttt{demo-catalog.yaml}); Metis populates the ABox automatically.

\begin{example}\label{example-2}
Horizontal scaling
\end{example}

This example evaluates ontology-driven closed-loop adaptation under load. The SLO is \textbf{850~ms} p95 entrypoint latency for all three applications (Sock Shop native \texttt{request\_duration\_seconds}; Online Boutique and BookInfo via Locust p95 exported to Prometheus). On violation, metrics-adapter asserts \texttt{ResponseTimeSlaViolatedState}; Palamedes plans \texttt{HorizontalScalingUpIntent}; Themis scales the entry Deployment to three ready replicas.

\subparagraph*{Discussion of Results.}
The semantic loop closes under the same SLA-style trigger on three different stacks, not only Sock Shop. Detection and scale-out times in Table~\ref{tab:paper_e2_scaling} are the operational-velocity evidence; CQ2 p95 in Table~\ref{tab:paper_e2_sparql} bounds GraphDB overhead inside that loop. Replica-seconds quantify extra capacity consumed during remediation. GraphDB and Palamedes RSS from \texttt{kubectl top} during the same runs give control-plane cost without a separate billing study.

\subsubsection*{Limitations}
The demo catalog maps vulnerable tags to fixed tags; it is not a production CVE-to-digest pipeline. SLOs are application-specific even when the numeric threshold is shared. All runs use one Kubernetes cluster. Minikube can reproduce SPARQL traces and control-loop timings, not the 14-node latency plots. Example~1 remediations require a Palamedes image built from this tree (extended \texttt{demo-catalog.yaml} and registry-qualified \texttt{kubectl set image}); a cluster still running an older Palamedes image will time out on the new Boutique/BookInfo pairs.
